# Flow Core: Ядро Асинхронного Управления Процессами (Workflow Engine)

Flow Core — это асинхронное ядро для управления сложными рабочими процессами (workflow engine) на основе Направленного Ациклического Графа (DAG). Архитектура построена на принципах явного контракта данных и декомпозиции ответственности.

## 🌟 Введение: Суть Концепции

Flow Core — это не просто код, это архитектурный подход, который превращает хаотичные, связанные между собой функции в чистый, управляемый, параллельный поток данных.

Представьте себе заводской конвейер:

- **Контракт (Contract)**: Это Рабочая Станция на конвейере. Она знает, что ей нужно на входе (сырье) и что она выдаст на выходе (готовый компонент), но ей неважно, кто будет использовать её результат.
- **Зависимость (Dependency)**: Это Трубопровод или Погрузчик, который точно знает, какие части результата одной станции должны быть доставлены на следующую, и под каким именем.
- **AsyncFlow (Планировщик)**: Это Диспетчер Завода. Он постоянно следит за всеми станциями и, как только у станции есть всё сырье, немедленно запускает её, а после завершения — распределяет её продукцию по всем зависимым трубам.

Наш главный принцип: **Порядок выполнения диктуется наличием данных.**

## 🛠️ Архитектурное Ядро: Четыре Столба

Flow Core построен на четырех ключевых абстракциях, которые гарантируют надежность и гибкость.

### 1. Contract: Атомарная Рабочая Станция

Каждый контракт выполняет единственную задачу (SRP).

| Элемент | Роль | Примечание для Профи |
| --- | --- | --- |
| `InputModel` | Pydantic Схема Входа. Определяет точные требования к данным (тип, формат). | Обеспечивает строгую валидацию перед запуском `logic`. |
| `OutputModel` | Pydantic Схема Выхода. Гарантирует структуру результата. | Обеспечивает валидацию результата после выполнения, предотвращая ошибки в нижестоящих контрактах. |
| `logic` | Функция, выполняющая работу. | Поддерживает синхронные и асинхронные функции; синхронные автоматически запускаются через `asyncio.to_thread()` для неблокирующего выполнения. |
| `required_inputs` | Буфер для сбора данных. Контракт запускается, когда все поля, необходимые для инстанцирования `InputModel`, собраны (проверка `is_ready()`). |  |

### 2. Dependency: Явный Маршрутизатор Данных

Это связь, которая отвечает только за поток данных и порядок.

- **Назначение**: Связывает `source` с `target`.
- **`mapping`**: `Dict[str, str]` – Главный инструмент. Позволяет взять `{"user_id": 123}` с выхода Источника и назвать его `{"user_id_for_notify": 123}` на входе Цели.

**🛑 Нюанс Многоцелевого Использования**
Один Контракт-Источник может быть использован сотнями других, и каждому из них он предоставит только ту часть данных, которая ему нужна.

### 3. AsyncFlow: Диспетчер и Исполнитель

Сердце системы, управляющее динамикой. Управляет всей системой, преобразуя плоский список Контрактов и Зависимостей в рабочий граф.

- **`run()`**: Главный асинхронный цикл. Постоянно ищет готовые Контракты (`is_ready()`) и запускает их параллельно через `asyncio.create_task`.
- **`_distribute_data()`**: Вызывается после успешного завершения Контракта. Использует `Dependency` для передачи `completed_contract.data` в `required_inputs` всех зависимых Контрактов.
- **Параллелизм**: Достигается через `asyncio.wait(return_when=asyncio.FIRST_COMPLETED)`. Позволяет избежать блокировки: планировщик ждет, пока любая задача завершится, а не ждет все сразу.
- **Разрешение Зависимостей**: Как только Контракт завершен, `AsyncFlow` немедленно вызывает `_distribute_data` для передачи его валидированных результатов всем ожидающим контрактам-целям.

## 3. Критические Нюансы и Особые Случаи

### Нюанс 1: Зависимость Только По Порядку

Для создания зависимости, которая не требует и не передает данных, используйте:

- `InputModel=EmptyData` и `OutputModel=EmptyData` в Контракте.
- `mapping={}` в `Dependency`.

Контракт с `EmptyData` будет считаться "готовым" с самого начала, если только у него нет других невыполненных зависимостей по порядку. Ядро `AsyncFlow` увидит, что `EmptyData` требует 0 полей, и сочтет этот вход удовлетворенным сразу, оставляя в силе только обязательство по порядку.

### Нюанс 2: Необходимость Pydantic

Pydantic предотвращает проблемы, когда выходные данные (`{'user_id': '123'}`) не совпадают с ожидаемыми типами (`user_id: int`) целевого Контракта. Если валидация Pydantic не удалась (ошибка `ValidationError`), Контракт немедленно переходит в статус `FAILED`, и процесс останавливается.

### Нюанс 3: Сборка Входных Данных

Целевой Контракт собирает свои данные (`required_inputs`) из двух мест:

- Начальные данные (`initial_data` при запуске `Flow.run()`).
- Выходные данные от всех Контрактов-источников через `Dependency`.
Контракт запустится, как только он получит все необходимые ключи, независимо от того, из скольких источников они пришли.

### Нюанс 4: Масштабирование

В текущей архитектуре:

- Горизонтальное масштабирование отсутствует (все выполняется в одном процессе/цикле).
- Для продакшена необходимо разделить `AsyncFlow` (Планировщик) и `Contract.execute` (Воркер), используя очередь сообщений (Kafka/RabbitMQ) для передачи задач.

### Нюанс 5: Автоматическое Сопоставление Данных (Wildcard Mapping)

Flow Core поддерживает упрощенный механизм сопоставления данных с использованием специального маркера `{"*": "*"}` в `Dependency.mapping`. Если этот маркер указан, система автоматически передаст все выходные ключи `completed_contract.data`, которые совпадают с ожидаемыми входными ключами `target.InputModel`, без необходимости явного перечисления каждого ключа. Это значительно упрощает конфигурацию зависимостей, когда имена полей совпадают между контрактами-источниками и контрактами-целями.

## 🛡️ Надежность и Дорожная Карта (Roadmap)

Текущий код является сильным ядром (PoC). Для Production-Ready внедрения требуются:

| Направление | Цель |
| --- | --- |
| **Устойчивость** | Persistence: Интеграция с БД (Postgres/Redis) для сохранения статуса после каждого шага и возможности возобновления процесса после сбоя сервера. |
| **Обработка Сбоев** | Retry Logic: Внедрение механизмов автоматических повторных попыток (`max_retries`) с задержкой при временных ошибках. |
| **Масштабирование** | Распределенное Выполнение: Разделение `AsyncFlow` (Планировщика) и `Contract.execute` (Воркера) с использованием очередей сообщений (Kafka/RabbitMQ) для горизонтального масштабирования. |
| **Наблюдаемость** | Мониторинг/Логирование: Полное логирование всех смен статусов, ошибок и времени выполнения. Экспорт метрик (Prometheus/Grafana). |
